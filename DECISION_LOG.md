# Decision Log

- 2026-08-18: Fixed private events returning "Event not found" for anonymous guests — added get_event_for_guest(uuid) SECURITY DEFINER RPC since events RLS had no policy allowing anon to read a private event row by UUID; App.jsx guest deep-link now calls this RPC instead of querying events directly.
- 2026-08-18: Fixed guest_sessions INSERT failing with 42501 for private events — replaced the raw correlated subquery in anon_insert_guest_sessions's WITH CHECK with a new check_guest_session_insert_allowed() SECURITY DEFINER function, since the raw subquery hit events RLS the same way and always returned zero rows for private events regardless of actual reveal_time.
- 2026-09-15: Fixed guest_sessions SELECT exposing every guest's email, taker_name, and device_fingerprint to any anonymous caller (anon_select_guest_sessions, qual = true, no row filtering) — dropped it, added host_select_own_guest_sessions (authenticated, scoped to host_id = auth.uid()) for the host dashboard's guest count, and get_guest_session(event_id, device_fingerprint) SECURITY DEFINER RPC for the two guest-facing resume-check reads. This also broke guest session creation itself (GuestEntry's insert-with-representation had no SELECT policy left to satisfy the RETURNING clause, failing every new session with 42501) — fixed with a matching create_guest_session(event_id, device_fingerprint, taker_name) RPC that returns the new id directly.
- 2026-09-16: Fixed photo uploads failing with 403 for every private, not-yet-revealed event — the storage.objects INSERT policy's WITH CHECK used a raw correlated subquery against events, evaluated under the anon caller's RLS context, same root cause as the 2026-08-18 guest_sessions INSERT fix but never applied to this policy. Replaced with check_storage_upload_allowed(event_id) SECURITY DEFINER function.
- 2026-09-16: Fixed guest_sessions photo-progress, completion, and email-capture updates silently no-oping for every guest (0 rows affected, no error) — anon_update_guest_sessions's WITH CHECK compared the row to itself via a self-referential subquery that resolved to NULL once anon_select_guest_sessions was dropped. Added update_guest_session_progress and update_guest_session_email SECURITY DEFINER RPCs, each verifying device_fingerprint inside the function body; all three call sites (takeShot, resume-check auto-complete, EmailCapture) swapped to them. The stale anon_update_guest_sessions policy was then dropped entirely rather than left in place bypassed, since it read as functional but permanently rejected everything.
- 2026-09-16: Fixed GuestEntry's resume-check always reporting 0 photos taken for a returning guest pre-reveal — its fallback (photoRows?.length ?? data.photos_taken) expected a failed photos query to return null/undefined, but an RLS-filtered read returns an empty array ([].length = 0), which ?? doesn't fall through on. Removed the photos-table query entirely; count now reads data.photos_taken directly from get_guest_session.
- 2026-09-16: Fixed GuestCamera crashing with "Rendered fewer hooks than expected" whenever done or cameraError became true — two useMemo calls were declared inline inside JSX only reachable via the final return, downstream of two earlier conditional returns that skip them. Hoisted both above the early returns.
- 2026-09-17: Fixed `storage.objects` upsert retries silently 403ing when a shot's path already had an object — no UPDATE policy existed at all (only INSERT). Added `Allow updates to valid event paths`, reusing `check_storage_upload_allowed(event_id)` (same function already backing the INSERT policy) for both `USING` and `WITH CHECK`. Verified live via `SET ROLE anon`: positive control overwrote an existing object at a private, not-yet-revealed event's path; negative controls confirmed a revealed event and a nonexistent event both still deny. `anon` already held table-level UPDATE grant, so this was purely an RLS-policy gap. Also verified end-to-end via the actual app client (real anon key, real Storage REST API, from the running dev server): first upload then retry against the same path returned the same object id with the retried bytes persisted.
